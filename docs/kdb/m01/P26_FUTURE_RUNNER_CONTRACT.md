## Observed local owner-transfer risk

PG17 allows transfer when the runner has a membership in `kdb_command_owner` with `SET TRUE` and the target has schema CREATE. That same membership allows `SET ROLE kdb_command_owner`, whose existing privileges include writes to protected tables. Therefore policy forbidding `SET ROLE` is not a database-enforced barrier. The proof returns `OWNER_TRANSFER_MEMBERSHIP_RISK`; it is not an approval to grant membership. A candidate alternative for Owner review is a separate short-lived, tightly audited transfer principal with precisely scoped role membership and a fixed allowlist of function identities; the creator has no membership in the function owner. Its powers and enforcement must themselves be proved before adoption.

The local PG17 membership comparison tested `INHERIT FALSE, SET FALSE`: both `SET ROLE` and `ALTER FUNCTION ... OWNER` failed with SQLSTATE 42501, and the owner stayed the creator. With `INHERIT FALSE, SET TRUE` both operations succeeded. This is a negative result for the approved single-principal model, not proof that all possible PostgreSQL role graphs have been exhausted. The unsafe owner transfer is blocked.
